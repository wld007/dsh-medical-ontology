# 临床本体构建 · 交接说明

> 给新会话的起点。先读 `docs/family.md`（插件家族与共同约定），再读本文件，再读 `docs/ontology-schema.md`（本体格式草案）。
> 上游格式见 `../dsh-medical-event/docs/event-package.md`。
> 整理于 2026-11-11。尚未写代码，也还没有效果图。

## 1. 一句话

读入 `dsh-medical-event` 交付的事件包，构建**患者级临床本体**：以每一次治疗决策为节点，把多年病程组织成 人／诊／治／伴／归（＋检／影），并标明每次决策如何引出下一次。
参照 G-MPAS 临床本体页（`docs/reference/gmpas-临床本体页.txt`，站点源码 `../www.g-mpas.com/ontology.html`）。

对应原八道工序的 **工序 5（问题线程）、工序 6（决策点）**，加上原工序里没有的**本体组装**。

## 2. 本体的五个部分（来自官网页）

| 部分 | 内容 |
|---|---|
| **人** 患者特征 | 人口学特征、器官功能与营养、患者意愿、社会支持与可及性、体能状态、治疗限制因素（器官功能、患者意愿、药品可及性）、末次随访 |
| **诊** 诊断与疾病关系 | 诊断分类：主要诊断、并发症、治疗相关不良事件、合并症；确定程度：确诊、临床诊断、疑似（随时间变化）；疾病关系六类：进展、治疗相关、加重、共存、风险相关、鉴别诊断；问题列表时间轴 |
| **治** 治疗与诊疗决策 | 主要疾病的治疗与合并症、并发症的处理分开记；每次决策是一个闭环：适应证 → 治疗方案 → 实际执行 → 短期（0–90 天）、中期（91–180 天）、长期（180 天以上）结局 → 后续治疗调整 |
| **伴** 伴发事件 | 治疗开始后发生、改变原定治疗的事件：新发疾病、不良事件、合并症加重、药品短缺、患者自行停药、中断治疗、要求转院；记录对主线的影响 |
| **归** 结局归因 | 每个结局在多大程度上来自某项治疗（份额），能否单独归因（可分离性），同期混杂因素 |
| 检／影 | 实验室检查、影像评估与治疗时间对齐 |

日期按距首次确诊的天数（D+n）表示。

|---|---|---|---|
| O1 读入事件包 | — | 校验格式版本、四道验收门、复核状态；记录上游批次 | 规则 |

| O3 决策节点 | 工序6 v1.1 | 治疗改变、关键流程、有新情况的维持；动作、同时安排、患者方决定、新情况、写明的理由、佐证、存疑；来源判定表；同期 7 天；同次就诊×同线合并 | 规则 |

## 4. 模型在这里是主力

工序 1–6 的原则是“不推断、不写因果”，本体的 归／伴／治疗相关不良事件 本质上是因果判断。处理办法：**每条结论标出处**（family.md §4.5）。

| 出处 | 怎么来 | 例 | 复核 |
|---|---|---|---|
| 原文写明 | 规则从原文抽出 | “因贫血停用卡铂” | 不需要 |
| 结构推出 | 按时间、同线计算 | 同期在用的其他治疗列为混杂候选 | 不需要，标“候选” |
| 模型判断 | 模型给结论，必须引用提及编号并通过原文核对 | “放射性肺炎 ← 胸部放疗，间隔 3.5 个月”、贡献份额 | 医生确认后才算数 |

- 模型可见时间 ＝ 所引证据中最晚的写成时间（as-of 用）。
- 建议模型＋核验模型；分歧进复核。
- 复核口径与因果链标注项目一致（`basis_records`、`confidence`、`confirmed_by`；见 `../因果链标注/README.md`、`contracts/tracks.yaml`、`skeletons.yaml`、`checks.yaml`）。该项目的“装配”（归线：每条记录至多一条主线、可多条支线、命不中进“未归线”）与 O2 高度重合，要对齐口径，避免两套规则。

## 5. 评测反推出来的必备字段

评测的 10 个任务都从本体派生（`docs/reference/gmpas-长病程评测页.txt`），所以本体必须事先存好：

| 任务 | 本体必须有 | 来源 | 缺口 |
|---|---|---|---|
| T01 后续结局 / T02 截至第 k 天 / T03 开环推演 | 治疗节点；三窗口结局；**主线标记**；检查节点；到下一主线节点的天数与原因类别 | 工序6、工序8 短期结局 | 主线、原因类别分类表、三窗口 |
| T04 下一步怎么做 | 决策原文、执行状态、首次执行日；**衔接说明单独存**（出题时隐去）；非临床因素（缺药、费用、拒绝）；8 类动作 | 工序6 动作与佐证 | 衔接说明、动作分类 |
| T10 并行治疗影响主线 | 伴发事件全链＋对主线影响五分类，**医生已确认** | — | 整条链新建 |
| T07 状态与诊断归类 | 诊断角色（主诊断/继发/不良事件/共病）、**确定程度历史**、某日在用治疗 | 工序2 确定程度、事件包用药片段 | 角色、历史 |
| T08 结局归因 | 归因表：每条治疗链×时间窗一行，**医生已确认** | 结构推出混杂候选 | 份额、可分离性 |
| T05 该说“不知道” | 末次接触日；被点名但无结果的检验 | — | 规则可算 |
| T06 医生当时知不知道 | 事件发生时间与首次写入时间分开 | 事件包已有 | — |
| T09 找矛盾 | 冲突登记（含不冲突反例） | 事件包 findings（`evalClass`） | — |

## 6. 病种差异（要用两个病种检验）

- 血透：问题线 P01–P13（肾脏替代、血管通路、容量与心衰、心律与抗栓、冠心病、血压、矿物质与骨代谢、肾性贫血、电解质与酸碱……，见工序5 设计）。
- 肺癌（官网样例，标“合成数据”）：主线是抗肿瘤治疗，其余为“其他治疗方向”。
- **未决：血透的“主线”是什么。** 肺癌有清楚的抗肿瘤主线，T01/T04/T10 都围绕它；血透是多条长期问题并行。可能的口径：每条长期问题线各有自己的“主线治疗节点”，或以肾脏替代线为主线。需与用户确认。
- 问题线词表、主线定义、原因类别、动作分类都放**病种层规则包**。

## 7. 界面（待画效果图，风格同 `dsh-medical-event/design/`）

- 产线：O1–O10，验收与复核状态。
- 问题列表时间轴：慢性问题贯穿全程，并发症与急性加重列在相关问题之下，独立发作单独成行；竖线是记录，方框是急性事件，灰带是住院，斜线是存疑（记录矛盾）期。
- 本体页：按 人／诊／治／伴／归／检／影 分区，同官网版式。
- 决策闭环卡片：适应证 → 方案 → 执行 → 三窗口结局 → 后续调整，每条可点回原文，并标出处（原文写明／结构推出／模型判断）。
- 伴发关系图：左主线、右其他方向，连线为伴发事件，中间标对主线的影响。
- 医生复核：逐条确认因果边、归因份额、诊断角色；显示两模型意见与引用原文。
- 规则包（病种层）、模型调用、日志、报告。

## 8. Agent 工具（草案）

`ontology_start`（输入为事件包目录）、`ontology_cancel`、`ontology_status`、`ontology_report`、`ontology_runs`。不能选模型端点。

## 9. 建议的第一步

1. 和 `dsh-medical-event` 对齐事件包格式（它是本插件唯一输入）。
2. 起草并定稿 `docs/ontology-schema.md`，用血透 HD-0001 与官网肺癌样例各填一份，检验两个病种都装得下；同时确认血透“主线”口径。
3. 画效果图（问题列表时间轴、本体页、决策闭环、医生复核）。
4. 再搭插件骨架，先做 O2、O3（纯规则）。


## 上游变更记录（dsh-medical-event）

- 2026-11-13 · dsh-medical-event 0.2.0：新增 **S00 格式识别**，非区域平台导出（其他 HIS／平台导出、字段为数据元编码、正文为 base64 XML 病历）也能出事件包。**事件包格式不变（event-package/0）**，但请注意：
  - `manifest.rulepacks` 里数据源层可能是 `recognized@<版本>`（自动识别）而不是 `zj-regional`；同一输入换了识别结果，版本号会变。
  - `recordType` 新增取值：生命体征、医嘱、处方、用药记录、治疗记录、申请单、收费、其他结构化；病程记录、会诊记录、手术麻醉记录、护理记录、转诊记录、其他文书。读取时不要假定只有原来 10 种。
  - 用药暴露（`exports/drug_exposure.csv`）现在也来自结构化医嘱／处方／给药记录，不只是文书转述。
  - 识别结果暂扣的表不进事件包；批次报告的「输入格式」一节列出了哪些表被采用、哪些暂扣。
